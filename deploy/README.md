# 部署说明

本目录记录**公网入口与容器编排**的部署要点。仓库内不含任何真实密钥、域名凭据或服务器凭据。

## 一、推荐拓扑

```
浏览器 ──► Cloudflare 边缘（代理模式，SSL 终止在边缘）
              │  回源 HTTP :80
              ▼
        云服务器 公网 :80
              │
              ▼
        esg-frontend (nginx)   ← 静态资源 + /api 反向代理
              │  ai-network（自定义 bridge 网络）
     ┌────────┼──────────┬────────────┐
     ▼        ▼          ▼            ▼
 esg-extractor  esg-agent2   esg-one-api   （均不映射宿主端口，只在内网互访）
```

要点：

- **入口只放行 80**。SSL 在 Cloudflare 边缘终止（SSL 模式选 Flexible），源站 nginx 只需监听 80，**无需签发与续期证书**，也不需要额外装 Caddy。
- **其余容器一律不映射宿主端口**，靠 `ai-network` 内网按容器名互访（`http://esg-extractor:8082` 等）。这样 8082 / 8083 / 3001 永远不会暴露到公网。
- 云厂商的**安全组 / 防火墙在网络层生效**，不落在主机 `iptables` 里。判断某个端口是否放行，要以**外部探针**结果为准，别只看 `ss -lntp`。

## 二、网络前置

```bash
docker network create --subnet 172.23.0.0/16 ai-network
```

子网刻意避开常见的 `172.17` / `172.18`，减少与宿主既有网段（VPN、校园网客户端等）冲突的概率。

## 三、启动

```bash
cp .env.example .env      # 填入 DeepSeek Key；如需大文件直传再填 COS 段
docker-compose up -d
curl -s http://127.0.0.1/api/health
```

`/api/health` 返回的 `build` 字段即当前系统版本，是判断部署是否成功最可靠的信号。

## 四、管理通道（可选）

若不想对公网开放 SSH，可用 **Cloudflare 命名隧道 + Access 服务令牌**把 22 端口"挂"到自己的域名上：

1. 先建 Access 应用与策略（仅允许服务令牌），**再**建 DNS 记录，最后才装隧道——避免出现"隧道已通但尚未鉴权"的裸露窗口；
2. 隧道跑成 systemd 服务并设 `Restart=always`，服务器重启后自动重连；
3. 客户端侧用 `cloudflared access tcp` 把远端 22 映射到本机回环端口，再照常 `ssh`。

> 这条通道与网站**完全解耦**：关掉客户端，网站毫发无损；服务器重启，隧道与网站各自自愈。

## 五、稳定性要点（实测结论）

- **容器重启策略用 `unless-stopped`**：宿主机重启后自动拉起。慎用 `always`——手工停掉的容器会被反复唤醒，反而难排查。
- **定时任务用 systemd timer 而非 cron**，并设 `Persistent=true`：机器在触发时刻处于关机状态时，开机后补跑一次。
- 免费版云服务若长期不活跃会被暂停，需安排**周期性真实读写探活**（每天打一次数据库的真实查询接口），单纯探健康检查端点不算"活动"。
